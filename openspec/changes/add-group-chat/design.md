## Context

本變更旨在將系統擴充為支援端對端加密（E2EE）群組聊天。這需要重構訊息金鑰的儲存結構，以支援一條訊息關聯多個收件者金鑰；同時，需要在後端新增群組管理的 REST API，並在 Socket.IO 中支援群組房間（Group Rooms）。

## Goals / Non-Goals

**Goals:**
- **群組端對端加密**：確保群組訊息在傳遞至伺服器前已被加密，且只有群組內的所有成員可解密。
- **統一的資料庫架構**：藉由重構金鑰儲存為 `message_keys` 關聯表，使私聊與群聊在資料庫設計上達到統一。
- **直覺的前端群組管理**：使用者可以在 UI 上直接點選多個聯絡人建立群組，並即時切換群聊。

**Non-Goals:**
- **超大型群組優化**：不針對百人以上群組設計 Sender Key (Signal 協議模式)，本系統將限制群組成員上限為 20 人。
- **群組管理員權限控制**：不實作群主、管理員、踢人等複雜權限，所有成員皆有相同權限。

## Decisions

### 1. 群組金鑰交換設計：Pairwise RSA 金鑰加密
- **選擇**：當發送訊息給群組時，發送端產生一個 AES 訊息金鑰，並使用群組內所有成員的 RSA 公鑰，將此 AES 金鑰加密 $N$ 次，產生 $N$ 個對應成員的金鑰包上傳。
- **原因**：相較於 Signal 協議使用的 Sender Key 鏈條管理，Pairwise 加密在成員數量少時實作極為簡單且安全。發送端只需在前端發送時執行多次 RSA 加密（因為 RSA 2048 加密在現代瀏覽器只需數毫秒），即可確保絕對的安全隔離，無須複雜的群組密鑰狀態同步。

### 2. 資料庫結構重構：正規化為 `message_keys` 關聯表
- **選擇**：移除原本 `Message` 表中的 `encrypted_key_sender` 與 `encrypted_key_receiver` 欄位。改為建立 `MessageKey` 資料表，欄位包含 `message_id`、`user_id`（有權限解密的使用者）、以及 `encrypted_key`。
- **原因**：這樣可以統一私聊與群聊的邏輯。不論是 Alice 與 Bob 私聊，或是 Study Group 群聊，當 Alice 發送訊息時，後端只需在 `MessageKey` 寫入各個授權接收者的金鑰封包。查詢歷史紀錄時，使用者只需查詢 `MessageKey` 中 `user_id == current_user.id` 的金鑰即可解密。

## Risks / Trade-offs

- **[Risk] 成員數量增加時的效能損耗**
  - *Mitigation*: 限制單一群組最多 20 人。當成員為 20 人時，發送一條訊息需進行 20 次 RSA 加密與寫入 20 筆金鑰記錄，這在現代瀏覽器與 SQLite 資料庫中約只需 15-30 毫秒，效能完全可接受。
- **[Risk] 重構資料庫模型導致舊訊息無法讀取**
  - *Mitigation*: 由於此專案為畢業專題展示，我們將直接在伺服器啟動時重建 SQLite 資料庫（`db.drop_all()` 與 `db.create_all()`），清空舊資料以進行全新部署。
